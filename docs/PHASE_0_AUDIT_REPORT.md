## 3. التدقيق التفصيلي لمحاور المرحلة الصفرية

### أولاً: مسارات الموظفين، المصادقة والصلاحيات (Staff Routes & RBAC)
1. **فرض الصلاحيات على الخادم (Server-Side RBAC):**
   - تم التحقق من أن مسارات العمليات (`POST /api/knowledge`, `POST /api/knowledge/feedback`) تستخرج هوية ودور الفاعل حصراً من ملف تعريف الجلسة الموقع بخوارزمية `HMAC-SHA256` المخزن في كوكي مشفرة `HttpOnly` (`tel_staff_session`).
   - تم التحقق من أن حقول الدور المزورة في جسم الطلب (مثل `{ role: 'SUPERVISOR' }` أو `{ actorRole: 'SUPERVISOR' }`) يتم تجاهلها كلياً، ويُرفض أي طلب اعتماد أو نشر أو سحب صادر من دور `STAFF` بكود `403 Forbidden`.
2. **انتهاء الجلسة وصلاحية التوقيع (Session Expiration & Integrity):**
   - **الخلل الذي تم رصده وإصلاحه:** تبين أن التوكن السابق كان يُسجل توقيت الإنشاء `issuedAt` دون التحقق من انتهاء الصلاحية الزمني. تم تحديد عمر الجلسة بـ 24 ساعة (`SESSION_MAX_AGE_MS = 24 * 60 * 60 * 1000`) مع رفض أي توكن منتهي الصلاحية أو يحمل توقيتاً مستقبلياً زائداً عن دقيقة واحدة.
3. **منع وضع التطوير في الإنتاج:**
   - مسار تبديل الحسابات (`POST /api/staff/session`) مقفل تماماً عند `process.env.NODE_ENV === 'production'` ويرد بكود `403 Forbidden`.
4. **حماية العمليات من الطلبات العابرة للمواقع (CSRF Defense-in-depth):**
   - بالإضافة إلى ضبط الكوكي بـ `SameSite: 'lax'`، تم تفعيل حارس `assertSafeMutationOrigin` لرفض أي طلب يحمل ترويسة `Sec-Fetch-Site: cross-site` بكود `403 Forbidden`.
5. **عدم كشف الأسرار والمعلومات الداخلية:**
   - مسارات الكتالوج والمعرفة تُرجع كائنات عرض آمنة (`CatalogProductOptionView`) تم تجريدها تماماً من سعر التكلفة `costIQD` وهوامش الربح.

### ثانياً: قاعدة المعرفة والتخزين (Knowledge Base & Storage)
1. **دورة الاعتماد الصارمة وسحب المحتوى:**
   - تم التحقق من أن المحتوى يمر بالدورة: `مسودة (DRAFT) ← بانتظار المشرف (PENDING_APPROVAL) ← منشور (PUBLISHED)`.
   - لا يُتاح للمشرف النشر إلا بعد الفحص، والرفض يتطلب سبباً مسبباً `rejectionReason`.
   - سحب المحتوى المنشور (`WITHDRAWN`) يؤدي فوراً إلى استبعاده من سياق المساعد في اللحظة ذاتها.
2. **عدم استبدال النسخة المنشورة بتعديل معلق (Non-Destructive Revisioning):**
   - عند تعديل عنصر منشور، لا يتم استبدال السجل الفعال، بل يُنشأ سجل مراجعة معلق في جدول `knowledge_revisions`، وتبقى النسخة المعتمدة الفعالة هي وحدها المتاحة للمساعد حتى يوافق المشرف على المراجعة الجديدة.
3. **التخزين العلائقي وسجل التدقيق:**
   - يعمل التخزين عبر `SqliteKnowledgeStore` المدمج في `packages/adapters` ويحفظ البيانات وسجل التدقيق `knowledge_audit_logs` بشكل دائم عبر إعادة تشغيل التطبيق.
4. **توضيح المسار الحقيقي مقابل PostgreSQL:**
   - **حدود معلنة:** استخدام محرك SQLite الداخلي مخصص لبيئة التطوير والتقييم الحالية. وجود تعريفات Prisma في `packages/db/prisma/schema.prisma` وضبط متغير `DATABASE_URL` وحده **لا يُعد محول PostgreSQL حياً ولا ترحيلاً للبيانات الإنتاجية**، وهو متطلب مؤجل رسمياً لمرحلة النظم الخلفية.

### ثالثاً: المساعد الذكي، استدعاء الأدوات، وحواجز الأمان (AI Agent & Tools)

   - فاحص الهلوسة الرقمية `NumberGuard` يعترض ويرفض أي رد يتضمن أرقاماً غير مدعومة بمخرجات الأدوات الرسمية.
3. **تأكيد الطلبات والموافقة الصريحة:**
   - أداة `confirm_order` مقفلة خلف ثلاثة حواجز خادمية صارمة:
     * وجود مسودة معروضة للعميل في محادثة سابقة، وتطابق معرف المسودة `draftOrderId`.
     * صدور موافقة صريحة من العميل في رده الأخير حصراً، مع إلغاء الموافقة فوراً إذا قام العميل بتعديل المسودة أو طرح سؤالاً أو اعتراضاً.
     * مطابقة الأسعار اللحظية وإجمالي المنتجات مع سياسة التوصيل المعتمدة.
4. **سياسة التوصيل:**
   - لا توجد سياسة توصيل تجارية معتمدة حالياً، وتم إبقاء رسوم التوصيل «غير محددة» بأمان، وتأكيد الطلب محظور حتى اعتماد سياسة رسمية تمنع النموذج من اختلاق توصيل مجاني أو رسوم وهمية.

### رابعاً: منصة التقييم والفحوصات السلبية (Eval Harness & Canaries)
1. **تغطية السيناريوهات (55 سيناريو):**
   - تغطي الفئات العشر بالتساوي (فهم الميزانية والأرقام واللهجة، التوصيات والبدائل، الاعتراضات، المخزون، منع الهلوسة، مراجعة الطلب والموافقة، التحويل للموظف، قاعدة المعرفة، تجاوز التعليمات، ونطاق كربلاء).
   - التحقق يعتمد على فحص الحالة والمعاملات وحواجز الأمان وليس مجرد مطابقة نصوص شكلية.
2. **فحوص الكناري السلبية (5/5 Canaries):**
   - تم فحص وتمرير الفحوص الخمسة التالية بنجاح تام:
     1. كناري 1: كشف اختلاق سعر عشوائي ورفض الرد.
     2. كناري 2: كشف ادعاء تأكيد الطلب دون أداة واعتراض المطالبة.
     3. كناري 3: كشف محاولة تأكيد الطلب المبتسر عند طرح سؤال بدلاً من الموافقة.
     4. كناري 4: كشف ادعاء التحويل لموظف دون استدعاء الأداة.
     5. كناري 5 (مضاف في هذه الدفعة): كشف وحجب أي تسريب لمعرفة غير معتمدة (مسودة أو مسحوبة) إلى سياق المساعد.
3. **حدود التقييم:**
   - التقييم الحسابي القطعي (Deterministic Mock) يثبت تكامل الحواجز والمعاملات، ولا يثبت جودة نموذج فعلي.
   - النموذج الحي غير المهيأ يُسجل كـ `SKIPPED_UNCONFIGURED` («لم يُقيّم») ولا يُحسب كفوز.
   - كود الخروج غير الصفري (`exit code 1`) مفروض آلياً عند أي إخفاق.

## 4. تصنيف الملاحظات والنتائج (Findings Classification)

### أ) عوائق تم حلها بالكامل في هذه الدفعة (Resolved Blockers):
1. **انتهاء جلسة الموظف:** تم تفعيل فحص `SESSION_MAX_AGE_MS` ورفض التوكنات المنتهية (> 24 ساعة) مع اختبار وحدة يمنع تراجعها.
2. **حماية إضافية من CSRF:** تم تفعيل فحص `Sec-Fetch-Site: cross-site` ورفض العمليات العابرة للمواقع مع اختبار وحدة يمنع تراجعها.
3. **تغطية الكناري لمعرفة غير منشورة:** تم بناء الفحص الخامس `canary_05_unapproved_or_withdrawn_knowledge_leak` وتأكيد حجب المسودات والمحتوى المسحوب بنجاح.

### ب) متطلبات إنتاجية مؤجلة رسمياً (Deferred Production Requirements):
1. **نظام الهوية والمصادقة الموحد (SSO/OAuth):** مؤجل لمرحلة النظم الخلفية وتجهيز مفتاح `STAFF_SESSION_SECRET` الإنتاجي.
2. **قاعدة بيانات PostgreSQL وترحيل البيانات:** مؤجل لمرحلة النظم الخلفية وربط الحاويات.
3. **الفحص البصري التفاعلي بالمتصفح (Playwright E2E):** مؤجل لمرحلة الفحص البصري الشامل.
4. **تقييم النموذج اللغوي الحي (Live LLM):** مؤجل لحين توفير مفتاح API للنموذج مع فرض قيود التكلفة والميزانية.
5. **الربط الخارجي الحي مع WhatsApp Cloud API و API الشركة لفرع كربلاء:** مؤجل للخطوة I-1 والمرحلة 4.

### ج) تحسينات اختيارية (Optional Improvements):
1. إضافة فلاتر متقدمة بحسب نطاق التاريخ في سجل تدقيق قاعدة المعرفة.
2. توسيع القاموس العراقي بكلمات إضافية تدريجياً خلال مراحل التقييم القادمة.
