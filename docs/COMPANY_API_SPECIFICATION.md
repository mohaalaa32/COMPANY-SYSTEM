## 2. المعلومات المطلوبة لربط نظام المبيعات وفق عقود المحولات (`ISalesAdapter`)

استناداً إلى عقود النظام المعتمدة في `docs/CONTRACTS.md §1` و `packages/adapters/src/types.ts`، يتطلب ربط كتالوج الشركة وأسعارها ومخزونها لفرع كربلاء استيفاء البنود التالية:

### أ) هوية وتصنيف المنتجات (Product Identity & Catalog Scope):
- **معرف الصنف المستقل (SKU / Barcode):** يجب أن يمتلك كل منتج معرفاً فريداً ومستقلاً يحدد الطراز، وسعة الذاكرة، واللون بدقة. يُمنع منعاً باتاً دمج أصناف متباينة في المواصفات تحت معرف واحد.
- **الاسم المعتمد:** الاسم الرسمي بالعربية (`nameAr`) وبالإنجليزية (`nameEn`).
- **الفئة والماركة:** تصنيف الجهاز (`phone`, `tablet`, `accessory`, `audio`, `wearable`) واسم الماركة الصريح (`Apple`, `Samsung`, `Xiaomi`, `Infinix`، إلخ).
- **الوسوم ومجالات الاستخدام:** أي وسوم تدعم أغراض الاستخدام (مثل: `gaming`, `student`, `best-camera`).

### ب) الأسعار، التكلفة، والعملة (Pricing & Margin Protection):
- **الأسعار:** سعر البيع الأساسي (`basePriceIQD`)، وسعر الخصم المعلن إن وجد (`salePriceIQD`).
- **سعر التكلفة الداخلي (`costIQD`):** مطلوب لاستخدامه حصراً من قبل محرك الحسابات القطعي (`@tel/calc`) لضمان عدم انتهاك الحد الأدنى للهامش الربحي (`minMarginPct`). يُعزل هذا الحقل تماماً ولا يظهر للعميل أو للواجهات الأمامية.
- **العملة والضريبة:** تأكيد أن الأسعار بالدينار العراقي (IQD)، وتوضيح ما إذا كانت الأسعار تشمل ضريبة المبيعات/الرسوم، أم تحتاج تحويلاً من عملة أخرى (كالـ USD).

### ج) مخزون فرع كربلاء وتوقيت البيانات (Karbala Stock & Latency):
- **معرف فرع كربلاء:** المعرف الرقمي أو النصي المعتمد لفرع كربلاء في نظام الشركة (لمطابقته مع `branch-karbala`).
- **طبيعة المخزون:** تحديد ما إذا كان الرقم المرجع يمثل «المخزون الإجمالي في الرف» أم «المخزون المتاح للبيع الفعلي بعد خصم المحجوز».
- **تحديث البيانات:** هل استعلام المخزون يتم لحظياً عبر API مباشر (On-demand)، أم يتطلب تخزيناً مؤقتاً (Cache TTL) محدد المدة، أم يرسل النظام إشعارات (Webhooks) عند تغير كميات الأصناف؟

### د) المواصفات، الضمان، ومصدر التجهيز (Specs & Agency):
- **المواصفات الفنية:** السعة التخزينية (Storage)، الذاكرة العشوائية (RAM)، المعالج (Processor)، الشاشة (Screen)، الكاميرا (Camera)، وسعة البطارية (Battery).
- **الضمان الرسمي (`warrantyMonths`):** تحديد مدة الضمان بالأشهر من حقل صريح ومستقل في بيانات الشركة. **يُحظر استنتاج الضمان أو نوعه من اسم المنتج**.
- **وكالة التجهيز ومصدر البضاعة:** إذا كانت الشركة توفر حقولاً للوكالة الرسمية أو الموزع المعتمد، تُربط كما هي، وإلا تُترك غير محددة بأمان ولا يتم اختلاقها.

### هـ) إمكانات وقدرات الواجهة البرمجية (API Capabilities):
- **القراءة (Read Capabilities):** استرجاع الكتالوج، وتفاصيل المنتج، والمخزون، والعروض النشطة.
- **الكتابة والحجز (Write / Transactional Capabilities):** يجب التحقق مما إذا كان API الشركة يدعم حجز المخزون مؤقتاً (`reserveStock`) أو إنشاء مسودة طلب، **أم أن API مخصص للاستعلام والقراءة فقط**. لا يجوز افتراض وجود ميزات حجز أو كتابة قبل ثبوتها في وثائق الشركة.

## 3. قائمة الطلب الرسمية الموجهة لمسؤول نظام شركة «تِل بغداد» (SysAdmin Request List)

> **صيغة الطلب الرسمي المقترحة للإرسال إلى مسؤول تقنية المعلومات / مدير النظام بشركة تِل بغداد:**

```text
السيد مسؤول الأنظمة والتقنية في شركة «تِل بغداد» المحترم،
تحية طيبة،

في إطار مشروع أتمتة وتطوير مساعد المبيعات الذكي لخدمة «فرع كربلاء»، نرجو تزويدنا بالمعلومات والوثائق الفنية اللازمة لربط نظام المبيعات والكتالوج، وفق النقاط المحددة أدناه:

1. وثائق الواجهة البرمجية والمسارات (API Documentation & Endpoints):
   - ملف توثيق الواجهة (Swagger / OpenAPI / Postman Collection أو ملف PDF).
   - الرابط الأساسي لبيئة الاختبار (Staging / Sandbox Base URL).
   - طريقة المصادقة المعتمدة (Bearer Token / API Key / OAuth2) وترويسات الطلب (Headers).
   - سياسات الاستخدام ومعدل الطلبات المسموح (Rate Limits) ونظام التصفح بالصفحات (Pagination).

2. بيانات فرع كربلاء (Karbala Branch):
   - المعرف الرسمي المعتمد لفرع كربلاء في نظامكم (Branch Code / ID).
   - توضيح ما إذا كان استعلام المخزون يتم لحظياً للفرع، أم يتطلب دورة تحديث مجدولة.

3. هيكل المنتجات والأسعار (Product Schema & Pricing):
   - نموذج استجابة (JSON Payload Sample) يحتوي على عينة حقيقية لـ 5 إلى 10 منتجات من أجهزة الهواتف والملحقات.
   - حقل المعرف الفريد للصنف (SKU / Barcode) وتأكيد استقلالية كل سعة ولون بمعرف منفصل.
   - معنى حقول الأسعار المتوفرة (سعر البيع، سعر الخصم، وسعر التكلفة الداخلي إن كان متاحاً لحساب الهوامش).
   - تأكيد عملة الأسعار (دينار عراقي IQD أم دولار USD) وما إذا كانت نهائية وشاملة لأي رسوم.

4. المخزون والمواصفات (Stock & Specifications):
   - حقل كمية المخزون: هل يمثل المخزون المتاح للبيع الفوري أم الإجمالي؟
   - حقول المواصفات المتوفرة (الذاكرة، الرام، اللون، الكاميرا، البطارية).
   - حقل الضمان المعتمد (عدد الأشهر أو نوع الضمان) إن كان مدعوماً كحقل مستقل.

5. إمكانات المعاملات (Transactional Capabilities):
   - هل تتيح الواجهة حجز المخزون مؤقتاً لطلب معلق (Stock Reservation)، أم تقتصر الخدمة الحالية على استعلام الكتالوج والمخزون الحي فقط؟

نؤكد التزامنا التام بعدم إرسال أو طلب أي مفاتيح إنتاجية أو بيانات سرية عبر قنوات الدردشة غير المشفرة، وسيتم ضبط المتغيرات التشغيلية محلياً عبر ملفات البيئة المعزولة (.env).

شاكرين تعاونكم معنا لإنجاح الربط التقني.
```

## 4. جدول المطابقة المبدئي بين نظام تِل بغداد ونظام الشركة (Field Mapping Matrix)

| حقل النظام المطلوب (`Product` / `ISalesAdapter`) | النوع المتوقع | حقل المصدر في نظام الشركة (يُحدد بعد الاستلام) | قواعد التحويل والتحقق (Transform & Validation) | الحالة والمعلومات الناقصة |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `string` | *قيد الانتظار* | معرف داخلي ثابت للنظام لا يتغير | بانتظار عينة الشركة |
| `sku` | `string` | *قيد الانتظار* | رمز SKU صريح ومستقل لكل لون وسعة | بانتظار عينة الشركة |
| `nameAr` | `string` | *قيد الانتظار* | اسم العرض العربي المعتمد | بانتظار عينة الشركة |
| `nameEn` | `string` | *قيد الانتظار* | اسم العرض الإنجليزي المعتمد | بانتظار عينة الشركة |
| `category` | `enum` | *قيد الانتظار* | مطابقة مع (`phone`, `tablet`, `accessory`, `audio`, `wearable`) | بانتظار دليل تصنيفات الشركة |
| `brand` | `string` | *قيد الانتظار* | استخراج الماركة الصريحة دون تخمين | بانتظار عينة الشركة |
| `basePriceIQD` | `number` | *قيد الانتظار* | عدد صحيح بالدينار العراقي (أكبر من صفر) | بانتظار تأكيد العملة والضرائب |
| `salePriceIQD` | `number?` | *قيد الانتظار* | عدد صحيح اختياري عند وجود خصم معتمد | بانتظار هيكل العروض والخصومات |
| `costIQD` | `number` | *قيد الانتظار* | عدد صحيح لحماية الهامش (معزول عن العميل) | بانتظار تأكيد توفر التكلفة |

| `branches[].quantity` | `number` | *قيد الانتظار* | كمية المخزون الفعلي المتاح للبيع (>= 0) | بانتظار تعريف طبيعة المخزون |
| `specs.storage` | `string?` | *قيد الانتظار* | مثل "128GB", "256GB" | بانتظار هيكل المواصفات |
| `specs.ram` | `string?` | *قيد الانتظار* | مثل "8GB", "12GB" | بانتظار هيكل المواصفات |
| `specs.color` | `string?` | *قيد الانتظار* | اسم اللون بالعربية | بانتظار هيكل المواصفات |
| `specs.warrantyMonths`| `number` | *قيد الانتظار* | عدد صحيح يمثل أشهر الضمان المعتمدة | بانتظار حقل الضمان الصريح |

## 5. خطة الخطوة القادمة I-2 (Next Step: I-2 Implementation Plan)

تُفعل الخطوة **I-2** فور استلام الوثائق والعينات، وتشمل:
1. إنشاء هيكل المحول الحقيقي `packages/adapters/src/sales/real-sales-adapter.ts` منفصلاً عن المحول التجريبي.
2. كتابة دوال التحويل وتجريد البيانات (`Data Mappers`) لمطابقة استجابات JSON الحقيقية مع واجهة `Product`.
3. كتابة اختبارات تكامل مبنية على عينات الاستجابة الحقيقية (Fixture-based Tests) دون الاتصال بالخادم الحي.
4. إعداد ملف التكوين النموذجي `.env.example` لبيان المتغيرات المطلوبة:
   - `TEL_SALES_API_BASE_URL`
   - `TEL_SALES_API_KEY`
   - `TEL_KARBALA_BRANCH_ID`
   - `TEL_SALES_API_TIMEOUT_MS`

## 6. المسارات المستقلة الممكن متابعتها أثناء انتظار توثيق الشركة (Feasible Tracks)

أثناء انتظار رد مسؤول نظام الشركة، يمكن متابعة الأعمال المستقلة التالية دون المساس ببيانات الربط:
1. **هندسة واجهات العميل ولوحة الموظفين (Phase 1):** تحسين تجربة المستخدم على شاشات الموبايل، حالات التحميل التفاعلية، ودعم إمكانية الوصول (A11y).
2. **محاكاة حالات فشل الشبكة والمهل (Resilience Testing):** كتابة سيناريوهات لاختبار سلوك النظام عند تعطل API المبيعات (503 Service Unavailable / Network Timeout) وضمان رد المساعد بلهجة عراقية مهذبة دون أعطال برمجية.
3. **توسيع بنك الأسئلة الشائعة في قاعدة المعرفة المحلية لفرع كربلاء.**
