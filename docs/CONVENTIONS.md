# معايير واتفاقيات التطوير — CONVENTIONS
**Tel Baghdad AI Sales Assistant (مساعد المبيعات الذكي لـ تل بغداد)**

---

## 1. قواعد الهوية والعلامة التجارية (Brand Rules - حاسمة جداً)

1. **المصدر الوحيد للحقيقة:** جميع النصوص المتعلقة باسم الشركة والمساعد وشعارها ورسائل الثقة تُستورد حصراً من `config/brand.ts`:
   ```typescript
   import { brand } from '@tel/config/brand';
   // أو نسبياً في الحزم الداخلية:
   import { brand } from '../../config/brand';
   ```
2. **المنع القاطع:** يمنع منعاً باتاً كتابة أي اسم تجاري قديم في الواجهات أو الكود أو التعليقات أو بيانات التهيئة أو الوثائق.
3. **الفحص الإجباري:** سكربت `pnpm check:brand` يفحص كامل المستودع للتأكد من خلوه التام، ويجب أن يمر بنجاح قبل أي اعتماد.

---

## 2. معايير تسمية الملفات والتعليمات البرمجية (Naming Conventions)

- **الملفات والمجلدات:** استخدام أسلوب `kebab-case` لجميع أسماء الملفات والمجلدات (مثل: `calc-engine.ts`, `sales-adapter.ts`, `chat-card.tsx`).
- **المكونات والواجهات والأنواع:** استخدام أسلوب `PascalCase` (مثل: `ProductCard`, `ISalesAdapter`, `OrderPayload`).
- **الدوال والمتغيرات:** استخدام أسلوب `camelCase` (مثل: `calculateInstallments`, `searchProducts`).
- **الثوابت العامة والتعدادات:** استخدام أسلوب `UPPER_SNAKE_CASE` (مثل: `DEFAULT_CURRENCY`, `MAX_RETRIES`).

---

## 3. معايير كتابة الشفرة البرمجية والتعامل مع الأخطاء (Error Handling)

1. **التحقق من البيانات (Input Validation):** استخدام مكتبة `zod` للتحقق الصارم من كل جسم طلب (Request Body) أو متغير وارد من العميل أو واجهات الـ API الخارجية.
2. **التعامل مع الأرقام والعمليات الحسابية:**
   - يمنع النموذج اللغوي (LLM) من إجراء أي عملية حسابية.
   - جميع الحسابات تجري في حزمة `packages/calc` باستخدام أرقام صحيحة (Integer Units) لتفادي أخطاء الفاصلة العائمة (Float issues).
   - التقريب للعملة العراقية (IQD) يعتمد دائماً خطوات الـ 250 أو 500 أو 1000 دينار عبر دالة `roundIraqiCurrency`.
3. **إدارة الاستثناءات:**
   - استخدام استثناءات معيارية محددة المسمى (`AppError`, `ValidationError`, `NotFoundError`, `MarginViolationError`).
   - تسجيل الأخطاء عبر هيكل بيانات منظم مناسب للمراقبة دون كشف أي أسرار في سجلات الأخطاء.

---

## 4. معايير الاختبارات وضمان الجودة (Quality Assurance - Agent 3)

- **اختبارات الوحدة (Unit Tests):** عبر إطار `vitest` لكل الحزم والخدمات.
- **اختبارات الخواص الرياضية (Property-Based Tests):** عبر مكتبة `fast-check` لمحرك الحسابات للتحقق من مئات الحالات الحدية (Edge Cases) والأرقام الكبيرة والأصفار والعملات.
- **اختبارات المتصفح الشاملة (E2E Tests):** عبر `Playwright` لمحاكاة تجربة العميل ولوحة الموظفين.
- **شرط الاعتماد:** أي خطوة لا تعتبر مكتملة إلا إذا كانت نتائج الفحص الثلاثية خضراء تماماً:
  ```bash
  pnpm lint
  pnpm typecheck
  pnpm test
  ```

---

## 5. قواعد توجيه النماذج والتصعيد (Model Routing & Escalation)

- النماذج السريعة (Gemini Flash / Gemini High) ملتزمة بعدم تغيير المعمارية أو تعديل ملفات العقود في `docs/CONTRACTS.md`.
- في حال واجه الوكيل خطأ أو تعثر مرتين متتاليتين في نفس المهمة:
  1. يتوقف فوراً عن المحاولات العشوائية.
  2. ينشئ ملف `docs/ESCALATION.md` يوضح فيه:
     - وصف المشكلة بدقة.
     - المحاولات التي تمت وسبب الفشل.
     - التشخيص والسبب الجذري المقترح.
     - ترشيح النموذج الأنسب لحل المشكلة (Opus أو High).
